# Storage Contract: IndexedDB 전적·기록 저장소 (v2)

테스트(`idb-battle-store.test.ts`, 메모리 저장소 가짜)와 수동 검증이 의존하는 저장소 계약이다. 이 계약이 v1의 `storage-contract.md`(localStorage)를 **대체**한다(OQ-3, FR2-020). v1 키 `rps-lab:score`는 **읽지도 쓰지도 지우지도 않는다**(AC2-045~047).

## 1. 데이터베이스

| 항목 | 값 |
|---|---|
| 이름 | `rps-lab` |
| 버전 | `1` |
| 저장소 | `battles`, `meta` |
| 네트워크 | 없음. 서버·외부 DB·로그인 없음(FR2-023) |

|---|---|---|
| `seq` (keyPath) | number | 양의 안전한 정수. 쓰기 트랜잭션 안에서 `마지막 키 + 1`(없으면 1) |
| `user` | `"rock"\|"paper"\|"scissors"` | 사용자 선택 |
| `computer` | 위와 같음 | 컴퓨터 선택 |

| 키 | 값 | 규칙 |
|---|---|---|
| `"stats"` | `{ wins, losses, draws }` | 0 이상의 안전한 정수. 파생 캐시 |
| `"probe"` | 임의 | 저장 다시 시도 중에만 존재 |

## 2. 저장소 인터페이스 (`BattleStore`)

UI와 실행 로직은 이 인터페이스에만 의존한다(IndexedDB 직접 호출 금지). 테스트는 메모리 구현을 주입한다. **실제 앱에서 UI와 자동 실행 모듈에 주입되는 것은 항상 큐로 감싼 `QueuedBattleStore`**다(3절).

```ts
interface BattleStore {
  loadStats(): Promise<Score>
  recordBattles(items: BattleDraft[]): Promise<Score>          // 확정 후 resolve, 갱신된 통계 반환
  listBattles(q: { before?: number; limit: number }): Promise<{ items: BattleRecord[]; hasMore: boolean }>
  clearAll(): Promise<void>
  probeWrite(): Promise<void>
}

// 앱 수준 FIFO 저장 큐 + 실패 게이트 + 복구를 더한 데코레이터 (save-queue.ts). 쓰기 메서드는 모두 큐를 거친다.
interface QueuedBattleStore extends BattleStore {
  whenIdle(): Promise<void>                               // 지금까지 수락된 쓰기가 모두 끝나고 그 결과가 호출 측에 전달된 뒤 resolve
  gate(): { closed: false } | { closed: true; cause: "read" | "write" }
  closeGate(cause: "read" | "write"): void
  recover(): Promise<Score>                               // 큐가 비어 있을 때만: 연결 새로 열기 → loadStats(검증) → probeWrite → 게이트 열기
}
```

| 메서드 | 트랜잭션 | 계약 |
|---|---|---|
| `loadStats` | 읽기(복구 필요 시에만 `readwrite`) | 연결당 **첫 호출**에서 불변식 1을 검증하고 어긋나면 `battles`를 스캔해 `meta.stats`를 다시 쓴다. 이후 호출은 `meta.stats`만 읽는다. 기록과 `meta`가 모두 비어 있으면 `0/0/0` |
| `recordBattles` | `readwrite` (`battles`+`meta`) | 한 트랜잭션에서 ① `meta.stats` 읽기 ② `seq` 부여 후 항목 전체 `add` ③ `meta.stats` 증가 `put`. **`oncomplete` 이후에만 resolve**한다(요청 성공이 아니라 커밋이 "확정"). 항목은 전부 저장되거나 전혀 저장되지 않는다. 입력 순서가 `seq` 순서다 |
| `listBattles` | 읽기 | `seq < before`인 레코드를 키 역순으로 최대 `limit`건. `hasMore`는 `limit+1`건을 읽어 판단. 읽은 레코드 수는 `limit+1` 이하이며 전체 건수와 무관 |
| `clearAll` | `readwrite` (`battles`+`meta`) | `battles.clear()`와 `meta.stats` 0 기록을 한 트랜잭션에서 수행. 레코드 내용을 읽지 않는다(손상 상태에서도 동작). 전부 성공하거나 전혀 변경되지 않음 |
| `probeWrite` | `readwrite` (`meta`) | `"probe"`를 쓰고 같은 트랜잭션에서 지운다. 쓰기 가능 여부만 확인 |
| `recover` (`QueuedBattleStore`) | 위 호출들의 조합 | **저장 다시 시도**의 구현. `whenIdle()` 뒤에만 실행하고 성공하면 게이트를 연다. 실패하면 게이트는 닫힌 채 `StoreError`로 거절 |

## 3. 순서·동시성 규칙

**데이터 정합성**(저장소 안의 기록·카운터가 서로 맞는가)과 **화면 최신성**(각 탭이 보여 주는 통계가 얼마나 최근 값인가)을 구분한다. 정합성은 항상 보장한다. 최신성은 P-9에 따라 실시간으로 보장하지 않으며 3.5절의 시점에 저장소 기준으로 갱신한다.

### 3.1 앱 수준 저장 큐 (G-1, G-4)
1. `getBrowserBattleStore()`가 돌려주는 객체는 **모듈 단위 단일 인스턴스**이며 FIFO 저장 큐, 실패 게이트, 연결 관리를 **소유**한다. 페이지 컴포넌트(`Game`, `History`)는 이를 **참조만** 하고 생명주기를 소유하지 않는다.
2. **모든 쓰기**(수동 저장, 자동 묶음, 초기화)는 이 큐를 거쳐 입력 순서대로 `seq`를 받는다(AC2-055). **자동 실행 모듈에도 큐로 감싼 저장소(`QueuedBattleStore`)를 주입한다**(원본 직접 주입 금지).
3. 읽기(`loadStats`, `listBattles`)는 큐를 거치지 않는다. 다만 페이지가 마운트되어 첫 읽기를 하기 전에 `whenIdle()`을 기다려 **이미 수락된 쓰기가 반영된 뒤** 읽는다(예: 수동 대결 직후 `/history`로 이동).
4. 페이지 언마운트(앱 내 이동)가 **이미 수락된 수동 저장을 조용히 폐기하지 않는다**. 큐에 수락된 요청은 계속 실행되어 커밋된다. 언마운트된 페이지는 그 결과를 표시하지 않는다. 결과는 **커밋된 뒤에만** 표시하는 규칙과 일치하며(표시 시점 = 확정 시점), 표시되지 않았어도 확정은 될 수 있다.
5. **브라우저 종료·새로고침·`pagehide` 시점에 아직 커밋되지 않은 기록(큐에서 대기 중이거나 진행 중인 쓰기)의 저장 완료는 보장하지 않는다.** 트랜잭션은 원자적이므로 커밋되었거나 아니거나 둘 중 하나이며 부분 저장은 없다.

### 3.2 저장 실패 게이트 (G-2, G-3)
1. 큐는 **실패 게이트**를 가진다. 쓰기가 `StoreError(kind="write")`로 실패하면 게이트가 닫히고, 큐에서 **아직 시작하지 않은 쓰기는 저장을 시도하지 않고** `StoreError(kind="skipped")`로 즉시 거절된다. 호출 측 해석: 수동 → 연습 대결로 처리(새 알림 없음), 자동 묶음 → 저장 실패 정책에 따라 실행을 `aborted`로 종료.
2. 초기 읽기(`loadStats`) 실패도 게이트를 닫는다(원인 `read`).
3. 게이트는 **`RETRY_SUCCEEDED` 시점에만 열린다**(`recover()` 성공). 앱 내 페이지 이동으로는 열리지 않는다: 게임 페이지로 돌아오면 닫힌 게이트에서 `unavailable(원인)`으로 시작한다(원인 `write`이면 통계를 읽어 표시하고, 원인 `read`이면 읽기를 시도하지 않고 `stats=null`). 새로고침은 새 JS 컨텍스트이므로 게이트를 새로 만들고 저장소를 다시 확인한다(Spec: 새로고침 후 저장소를 다시 확인).
4. **자동 실행 시작 전 큐 유휴 확인(G-3)**: 시작 요청은 먼저 `whenIdle()`을 기다려 큐에 남은 수동 저장의 결과가 모두 reducer에 도달한 뒤 수락한다. 그동안 들어온 중복 시작 요청은 무시한다. **시작 후 실행 중 발생한 저장 실패(게이트 포함)는 자동 실행의 저장 실패 정책으로 처리**한다(실행 종료 `aborted`, 확정된 묶음까지만 반영, AC2-057).

### 3.3 중지·이탈·초기화 (G-5, G-6, G-8, G-9)
1. **중지**: `abort()`는 **묶음 사이에서만** 반영된다. 이미 시작된 묶음은 끝까지 저장되어 커밋되면 포함, 아니면 완전 제외된다(AC2-016).
2. **중지 중 저장 실패(G-8)**: `stopping` 상태에서 저장 실패가 발생하면 **저장 실패로 인한 `aborted`가 우선**한다. 요약은 `stopped`가 아니라 `aborted`다.
3. **즉시 결과의 이탈(G-9)**: 즉시 결과 실행에도 같은 `abort()`가 앱 내 이동(언마운트)과 `pagehide`에서 호출된다. 이미 **커밋된 묶음까지만** 확정 기록으로 남고 나머지는 시작하지 않는다.
4. **초기화와 이탈(G-5)**: `clearAll`은 큐에서 앞선 쓰기가 끝난 뒤 실행되며 취소할 수 없다. 실행 중 페이지를 떠나면 트랜잭션은 **전부 적용되거나 전혀 적용되지 않는다**. 이는 원자성에 대한 설명이며 이탈이 초기화의 성공적 완료를 보장한다는 뜻이 아니다. 어느 쪽이든 다음 진입 때 저장소를 읽어 결과를 확인한다.
5. **초기화와 재시도의 상호 배제(G-6)**: 초기화가 진행 중(`reset≠idle`)이면 저장 다시 시도를 시작할 수 없고, 재시도 중(`retry=retrying`)이면 초기화를 요청할 수 없다. 둘 다 같은 연결과 게이트를 다루기 때문이다.

### 3.4 확정 순서와 화면 반영 순서 (G-11)
- 큐의 FIFO 순서가 곧 확정 순서이며 `COMMITTED`/`RUN_PROGRESS`/`SAVE_FAILED`는 그 순서대로 reducer에 전달된다.
- 자동 실행은 시작 전에 큐가 비어야 하므로(3.2의 4) **시작 전에 큐에 있던 수동 저장의 커밋은 정상 반영**된다(전적과 `last`). 그 뒤 자동 실행의 진행이 `last`를 갱신한다. `RUN_STARTED`는 선행한 모든 `COMMITTED`/`SAVE_FAILED`가 도달한 뒤에 일어난다.

### 3.5 여러 탭
- **정합성(항상 보장)**: IndexedDB `readwrite` 트랜잭션은 직렬화되고, `seq`는 트랜잭션 안에서 부여되며, 카운터는 기록과 같은 트랜잭션에서 갱신된다. 따라서 탭 조합과 무관하게 `seq` 중복, 기록 유실, 카운터 어긋남이 없다. 한 탭이 초기화하면 다른 탭의 이어지는 쓰기는 비워진 저장소에 `seq=1`부터 쌓인다.
- **화면 최신성(실시간 보장 안 함, P-9)**: 각 탭의 통계는 다음 시점에 저장소 기준 값으로 갱신된다: ① 페이지 마운트 ② 자신의 쓰기 응답 ③ 초기화 성공 ④ 저장 다시 시도 성공 ⑤ 새로고침. ②의 응답 통계는 다른 탭의 쓰기까지 포함한 저장소 값이므로 합계가 한 번에 여러 건 늘어 보일 수 있다. 탭이 다시 보일 때의 자동 갱신, `BroadcastChannel`, `storage` 이벤트 같은 실시간 동기화는 요구사항 범위 밖이라 쓰지 않는다.
- **선택 제안(현재 추가하지 않음, 구현·검증 단계에서 필요 시 재검토)**: 탭이 다시 보일 때 통계(와 기록 첫 페이지)를 한 번 갱신. 사용자가 조작하지 않아도 숫자가 바뀌는 UX 변경이므로 지금은 넣지 않는다.

## 4. 오류 매핑

모든 저장소 예외는 `StoreError`로 정규화한다. 호출 측은 `kind`만 보고 화면 상태를 정한다.

| 상황 | `kind` | 화면 결과 |
|---|---|---|
| `indexedDB` 없음, `open` 오류·차단, 시크릿 모드 제한 | `unavailable` | 읽기 실패와 같은 처리(저장 불가·읽기) |
| 통계·목록 읽기 중 트랜잭션 오류 | `read` | 저장 불가(읽기) 또는 기록 오류 상태 |
| 쓰기 트랜잭션 `abort`/`error`(용량 초과 `QuotaExceededError`, 제약 위반 포함) | `write` | 저장 실패 → 저장 불가(쓰기) |
| 레코드·카운터 형식 위반, 복구 스캔 중 손상 레코드 | `corrupt` | 저장 불가(읽기). 전적 초기화로 탈출 가능 |
| 저장된 DB 버전이 코드 버전보다 높음(`VersionError`) | `version` | 저장 불가(읽기). 데이터를 건드리지 않음 |
| 실패 게이트가 닫혀 있어 저장을 시도하지 않음 | `skipped` | 수동: 연습 대결로 처리(새 알림 없음). 자동 묶음: 저장 실패 정책(`aborted`) |

### 연결 관리 (G-7)
- **개별 트랜잭션 오류와 연결 무효화를 구분한다.** 트랜잭션의 `abort`/`error`(용량 초과, 제약 위반 등)는 연결을 무효화하지 않는다. 연결은 유효한 채로 두고 **불필요하게 닫지 않는다**.
- 연결을 **무효화**하는 경우는 다음뿐이다: (a) `versionchange`(다른 탭의 업그레이드 요청 → `db.close()`, 진행 중인 트랜잭션이 끝난 뒤 닫힘), (b) 연결의 `close` 이벤트(비정상 종료, 예: 저장소 삭제), (c) `db.transaction()`이 `InvalidStateError`로 실패, (d) `open` 실패(실패한 연결은 캐시하지 않음).
- 무효화된 연결은 캐시에서 비우고 **다음 새 요청부터** 새로 연다. **이미 진행 중인 요청은 각자 자신의 트랜잭션 핸들을 가지고 있으므로 강제로 종료하지 않는다**(끝나거나 스스로 실패).
- **연결 세대 번호는 도입하지 않는다.** 각 요청이 시작될 때 연결 약속(Promise)을 자신이 잡고, 무효화 이벤트는 캐시 참조가 *그 연결과 같을 때만* 비우는 동일성 비교로 충분하다(오래된 연결의 늦은 이벤트가 새 연결을 지우는 문제를 막음). 재연결이 겹치는 상황 등 세대 번호가 꼭 필요한 경우가 구현에서 관찰되면 그때 근거와 함께 도입한다.
- `recover()`만 예외적으로 현재 연결을 **의도적으로 새로 연다**. 큐가 비어 있고(`whenIdle`) 초기화가 진행 중이 아닐 때만 실행되므로 다른 요청을 끊지 않는다.

## 5. 스키마 변경과 마이그레이션 전략

- 마이그레이션은 `onupgradeneeded`에서 `oldVersion + 1`부터 `newVersion`까지 **번호순 단계 함수**를 차례로 실행한다. 한 번 배포된 단계는 수정하지 않고 새 단계를 추가한다.
- **버전 1 단계**: `battles`(keyPath `seq`)와 `meta`를 만든다. **기존 데이터 이전은 없다**. 첫 설치이며 v1 localStorage 전적은 이전하지 않는다(OQ-3).
- 이후 변경은 추가 방향(필드·인덱스 추가)을 기본으로 한다. 필드를 추가할 때는 읽기 검증이 이전 레코드를 허용해야 한다.
- 더 낮은 버전 코드가 높은 버전 DB를 여는 경우(다운그레이드)는 `version` 오류로 읽기 불가 처리하며 DB를 변경하지 않는다.

## 6. v1 localStorage와의 관계 (AC2-045~047)

- v2는 `localStorage`를 사용하지 않는다. 키 `rps-lab:score`가 있거나 손상돼 있어도 접근하지 않으므로 어떤 영향도 없다.
- `score-storage.ts`는 구현 단계에서 제거한다(미사용 코드 남기지 않음).

## 8. 호스팅 환경(GitHub Pages)에서의 저장소 범위

- IndexedDB는 **출처(origin)** 단위다. 배포 주소가 `https://hyeonseoman.github.io/rps-lab/`이면 출처는 `https://hyeonseoman.github.io`이며 **이 계정의 다른 GitHub Pages 프로젝트 사이트와 같은 출처를 공유**한다(경로가 달라도 같은 출처의 저장소를 볼 수 있다). DB 이름 `rps-lab`은 이 앱의 이름공간이며 다른 사이트가 같은 이름을 쓰지 않는 것을 전제로 한다. 개인정보를 저장하지 않으므로(FR2-023) 위험은 낮다.
- 정적 호스팅과 IndexedDB는 호환된다(브라우저 API이며 서버가 관여하지 않음). HTTPS 출처이므로 보안 컨텍스트 요구도 충족한다. 배포 주소가 바뀌면 출처가 바뀌어 기존 기록은 보이지 않는다(이전 기능 없음, OQ-3와 같은 방침).
- 브라우저의 장기 미사용 저장소 정리·퇴출은 v2 범위 밖으로 수용한다(plan RK-1).
