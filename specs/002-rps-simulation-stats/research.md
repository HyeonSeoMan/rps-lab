## R-01. IndexedDB 접근 방식

- **결정**: 브라우저 `indexedDB`를 직접 사용하고, Promise 헬퍼 약 100줄을 `src/lib/idb-battle-store.ts` 안에 둔다. 외부 래퍼 라이브러리를 쓰지 않는다.
- **근거**: 스키마가 저장소 2개(`battles`, `meta`)와 트랜잭션 5종뿐이다. 래퍼가 주는 이점(편의 API)이 작고, Constitution II(불필요한 라이브러리 금지)에 맞는다. 트랜잭션 완료 시점(`oncomplete`)을 직접 다뤄야 "저장 확정"을 정확히 정의할 수 있다.
- **대안**: `idb`(작은 래퍼): 편하지만 의존성 추가이고 이점이 작다. `Dexie`: 기능 과다. 둘 다 기각.

## R-02. 누적 통계를 어떻게 얻는가 (Spec: "매번 계산 vs 갱신 저장"을 Plan에 위임)

| 방식 | 호환성 | 복잡도 | 성능 | 데이터 안정성 | 테스트성 |
|---|---|---|---|---|---|
| A. 매번 전체 스캔 집계 | 단순 | 낮음 | **나쁨**: 10만 건이면 대결마다 O(n) | 항상 일치 | 쉬움 |
| B. 인덱스 `count()` 3회 | 단순 | 낮음 | 보통: 키 범위 순회 비용이 n에 비례할 수 있고 측정 전 불확실 | 항상 일치 | 쉬움 |
| **C. 기록과 같은 트랜잭션에서 갱신하는 카운터 + 연결당 1회 검증·복구** | 중간 | 중간 | **좋음**: 읽기 O(1), 쓰기 O(묶음) | 트랜잭션이 원자적이라 구조적으로 일치. 검증이 어긋남을 감지하고 기록 기준으로 재계산 | 중간 |

- **결정**: **C**. `battles`가 유일한 진실의 원천이고 `meta.stats`는 파생 캐시다. 같은 `readwrite` 트랜잭션에서 함께 갱신하므로 "기록 없이 카운터만 증가" 같은 상태가 생길 수 없다. 연결을 열고 첫 `loadStats`에서 `승+패+무 === battles.count()`를 검증하고, 어긋나면 기록을 스캔해 카운터를 다시 만든다(FR2-020 "저장된 개별 기록 기준").
- **근거**: 자동 대결 1,000회와 10만 건 규모(P-8)에서 A는 비현실적이다. B는 측정 전에는 성능을 보장할 수 없다. C는 B를 "검증용 count 1회"로만 쓰므로 비용이 연결당 1회다.
- **위험**: `count()` 비용이 10만 건에서 느리면 검증을 생략하거나 지연한다(plan.md 위험 RK-4, 측정 M-08로 판단).

## R-03. 기록 페이지네이션

- **결정**: **키셋(커서) 방식**. `seq` 키의 역순으로 `before` 기준 이전 값부터 `limit+1`건을 읽는다. "이전"은 메모리에 둔 앵커 스택에서 꺼낸다. 이동은 이전/다음뿐이라 임의 페이지 점프가 필요 없다(OQ-5).
- **근거**: 읽는 양이 페이지 크기(20)에만 비례하고 n에 무관하다(FR2-014, SC2-003). 중간에 기록이 추가돼도 앵커 기준이라 누락·중복이 없다(AC2-027).
- **대안**: offset 방식(`advance(n)`)은 뒤 페이지일수록 느려서 기각. `getAll` 후 슬라이스는 전체를 메모리에 올려 FR2-013·014 위반이라 기각. `seq` 산술 범위(`N-20p`)는 연속성 가정에 의존해 기각.

## R-04. 상태 관리 구조

| 방식 | 호환성 | 복잡도 | 테스트성 | 비고 |
|---|---|---|---|---|
| A. `useReducer` + effect 안에서 비동기 처리 | 높음(v1 패턴) | 낮음~중간 | 낮음: 타이머·큐·취소가 컴포넌트에 얽힘 | 경쟁 상태를 컴포넌트 테스트로만 검증해야 함 |
| **B. `useReducer`(순수 reducer) + 프레임워크 무관 비동기 모듈(`save-queue`, `auto-runner`)** | 높음 | 중간 | **높음**: 비동기 로직이 React 없이 테스트됨 | Constitution VI 취지에 부합 |
| C. 클래스 컨트롤러 + `useSyncExternalStore` | 낮음 | 높음 | 높음 | 자체 스토어를 새로 만드는 셈 |

- **결정**: **B**. 상태 전이는 순수 reducer(`game-session.ts`), 비동기 흐름(순차 저장 큐, 자동 실행 반복)은 React를 모르는 모듈로 분리하고 훅(`useGameSession`)이 둘을 연결한다.
- **근거**: 가장 위험한 부분(중지·취소·저장 실패·순서 보장)을 jsdom 없이 빠르게 검증할 수 있다. v1의 `useReducer` 구조와 일관된다.

## R-05. 저장 단위(자동 대결)

- **결정**: 자동 대결은 **묶음 트랜잭션**으로 저장한다. 애니메이션은 틱마다 1묶음(`ceil(N/100)`건), 즉시 결과는 100건씩 묶는다. 수동 대결은 1건씩이다.
- **근거**: 1,000회를 1건씩 트랜잭션으로 저장하면 느리고, 1,000건을 한 번에 저장하면 실패 시 전부 잃고 중지도 불가능하다. 묶음 단위도 원자적이므로 "각 대결은 전부 저장되거나 전혀 저장되지 않는다"(AC2-037)와 "중지 순간 저장 중이던 대결은 확정되면 포함, 아니면 제외하며 부분 반영 없음"(AC2-016)을 만족한다. 실패가 묶음 하나(최대 100건)로 한정된다.
- **대안**: 1건씩 저장: 정확하지만 즉시 결과가 느림(1,000회 × 트랜잭션 왕복). 전체 1회 저장: 단순하나 실패 영향이 크고 애니메이션 중지와 맞지 않음. 둘 다 기각.

## R-06. 애니메이션 스케줄 (OQ-1 "1,000회도 과도하게 오래 걸리지 않게")

- **결정**: 틱 간격 70ms 고정. 묶음 크기 `max(1, N/100)`건 → 10회 약 0.7초, 100회·1,000회 약 7초. 틱마다 묶음을 저장한 뒤 마지막 대결을 화면에 표시하고 진행 횟수를 갱신한다.
- **근거**: 기본 간격 "약 70ms"(OQ-1)를 지키면서 1,000회를 약 7초로 제한한다. 표시를 묶는 것은 AC2-014가 허용한다. 진행 횟수 = 확정된 수가 항상 일치한다.
- **조정 여지**: 상수는 `auto-run.ts`에 모으고, P-8 측정 후 사용자와 합의해 조정한다.

## R-07. 자동 대결 중지·이동·새로고침

- **결정**: `AbortController` 하나를 실행마다 만든다. 중지 버튼, 컴포넌트 언마운트(앱 내 이동), `pagehide`가 모두 같은 `abort()`를 호출하며 **즉시 결과 실행에도 똑같이 적용**한다(G-9). 실행 모듈은 **묶음 사이**에만 신호를 확인한다. 이미 시작된 묶음 저장은 끝까지 진행한다. **중지 중 저장 실패가 있으면 저장 실패로 인한 `aborted`가 우선**한다(G-8). 새로고침은 별도 처리 없이 JS 상태가 사라지고 저장 완료분만 남는다(커밋되지 않은 기록의 완료는 보장하지 않는다, G-4).
- **근거**: 트랜잭션을 중간에 끊지 않으므로 원자성이 깨지지 않는다. 진행 중인 저장이 확정되면 포함, 아니면 제외한다(AC2-016). 재개 코드를 만들지 않으므로 "자동 재개 금지"(OQ-2)가 구조적으로 보장된다. 저장 실패는 데이터 문제이므로 사용자 동작(중지)보다 먼저 보고되어야 한다.
- **대안**: `beforeunload`에서 저장 대기: 새로고침을 막거나 불확실. 기각.

## R-08. 확인 대화상자 구현 방식 (U5: 화면 내 커스텀 대화상자)

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 네이티브 `<dialog>` + `showModal()` | 포커스 트랩·`Esc`·배경 비활성화를 브라우저가 제공 | **jsdom 29.1.1에 `showModal` 없음** → 자동 테스트에 폴리필 필요. 최종 HTML(`rps-lab-v2-ui.html`)의 오버레이 위치·모양과 맞추려면 추가 CSS |
| **B. 직접 구현(`role="alertdialog"`)** | 최종 HTML과 같은 구조. jsdom에서 포커스 이동·`Esc`·Tab 순환을 키보드 이벤트로 자동 검증 가능 | 4가지 접근성 요구를 직접 구현해야 함 |

- **결정**: **B**. 최종 HTML에서 이미 구현·검증한 방식을 따른다: 열릴 때 취소 버튼으로 포커스 이동, 앱 헤더·본문에 `inert`, Tab/Shift+Tab 순환(`inert` 미지원 환경 보강), `Esc`로 닫기, 닫히면 연 버튼으로 포커스 복원.
- **근거**: jsdom이 `inert`와 `showModal`을 구현하지 않으므로 어느 쪽이든 실제 `inert` 동작은 브라우저에서만 검증된다(수동 M-05). B는 포커스 이동·`Esc`·순환 로직을 jsdom에서 자동 검증할 수 있다.
- **대안 검토**: A는 구현량이 적지만 테스트 폴리필이라는 새 부담이 생기고 시각 레퍼런스와 어긋난다.

## R-09. 반응형: 표 ↔ 카드 목록 전환

- **결정**: `@container`(컨테이너 폭 600px 이하, U4)를 쓰고, 목록은 **표와 카드 두 DOM을 모두 렌더**한 뒤 CSS `display:none`으로 한쪽을 숨긴다. 컨테이너 쿼리는 컨테이너 자신의 스타일을 바꾸지 못하므로 패딩은 안쪽 요소가 가진다(최종 HTML에서 확인한 함정).
- **근거**: `display:none`은 접근성 트리에서 빠지므로 스크린리더에 중복 노출되지 않는다. JS 측정(ResizeObserver)이 필요 없다. 20건이라 DOM 중복 비용이 무시된다.
- **대안**: `ResizeObserver`로 한쪽만 렌더: jsdom에 `ResizeObserver`가 없고 하이드레이션·타이밍 복잡도가 늘어 기각. 하나의 표 마크업을 CSS로 카드처럼 보이게: 표 의미(role)가 깨지는 알려진 문제라 기각.
- **테스트 영향**: jsdom은 컨테이너 쿼리를 평가하지 않는다. 표/카드 전환은 수동(M-03)이며 자동 테스트는 두 마크업이 같은 기록을 같은 순서로 담는지만 검증한다.

## R-10. IndexedDB 테스트 방법 (새 개발 의존성 필요성)

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 의존성 없이 실브라우저(CDP)로만 검증 | 새 패키지 없음 | 재현·자동화 어려움, 트랜잭션 원자성·실패 주입 같은 핵심 위험을 CI형 테스트로 못 잡음 |
| B. 직접 만든 가짜 IndexedDB | 의존성 없음 | 트랜잭션·커서·중단 의미를 자체 구현해야 해 그 자체가 위험 |
| **C. `fake-indexeddb`(devDependency)** | 트랜잭션·커서·`abort`를 표준 의미로 구현. 어댑터 테스트에 한정 | 새 개발 의존성 1개 |

- **결정**: **C를 어댑터 테스트(`idb-battle-store.test.ts`)에만 사용**한다. UI·실행 로직 테스트는 의존성 없는 **메모리 저장소 가짜**(`BattleStore` 인터페이스 구현)로 수행한다.
- **근거**: 데이터 정합성(원자성, 초기화, 키셋 페이지네이션, 복구)이 이 기능의 최대 위험이며 Spec(P-8)도 jsdom에 IndexedDB가 없어 가짜 라이브러리가 필요할 수 있음을 짚었다. 런타임 번들에는 들어가지 않는다.
- **상태**: **승인됨(2026-11-05)**. Constitution II에 따라 [plan.md의 Complexity Tracking](plan.md#complexity-tracking)에 정당화를 기록했고 설치는 구현 단계에서 한다. 문제가 생기면 사용자에게 보고하고, 대안은 실브라우저 수동·CDP 검증이다.

## R-11. 라우트와 공통 헤더

- **결정**: App Router 라우트 2개: `/`(게임), `/history`(기록·통계). 공통 헤더(`AppHeader`)를 `layout.tsx`에서 렌더하고 탐색은 `next/link` + `usePathname`으로 `aria-current="page"`를 표시한다.
- **근거**: Spec이 "별도 기록·통계 페이지"와 "앱 내 페이지 이동"을 전제한다. 라우트를 나누면 이동 시 게임 페이지가 언마운트되어 자동 중지가 자연스럽게 일어난다(R-07).
- **대안**: 한 페이지 안의 탭 전환: 이동이 아니라 숨김이라 자동 대결이 계속되어 AC2-059를 별도 로직으로 맞춰야 해서 기각.

## R-14. 저장 다시 시도의 검증 범위 (FR2-025)

- **결정**: 재시도(`QueuedBattleStore.recover()`)는 큐가 비어 있고 초기화가 진행 중이 아닐 때만 실행하며 ① 연결을 새로 열기 ② 통계 읽기(검증 포함) ③ `meta`에 임시 키 쓰기·삭제(같은 트랜잭션)를 모두 성공해야 복구로 판정하고 그때 **실패 게이트를 연다**(G-2, G-6).
- **근거**: 읽기만 성공하는 저장소(용량 초과 등)에서 거짓 복구를 줄인다. 다른 요청이 없을 때만 연결을 새로 열므로 진행 중인 요청을 끊지 않는다(G-7).
- **한계**: 아주 작은 쓰기는 성공하고 이후 큰 쓰기가 실패하는 경계 상황은 복구 판정 뒤 다시 저장 실패 상태가 될 수 있다. 이 경우 AC2-057/039 흐름이 다시 적용된다(허용).

## R-17. 저장 큐·실패 게이트의 소유권 (G-1~G-4, G-11)

- **결정**: FIFO 큐, 실패 게이트, 연결 관리를 **모듈 단위 단일 인스턴스**(`getBrowserBattleStore()`)가 소유한다. 페이지는 참조만 한다. 게이트는 `recover()` 성공에서만 열리고, 자동 실행 시작은 `whenIdle()` 뒤에만 수락한다. 언마운트는 수락된 수동 저장을 폐기하지 않는다. 자동 실행 모듈에도 큐로 감싼 저장소를 주입한다.
- **근거**: 큐가 페이지 컴포넌트의 생명주기에 묶이면 이동 시 수락된 저장이 폐기되거나 순서가 깨진다. 게이트가 페이지 상태에만 있으면 이동 후 복귀가 저장 불가 상태를 풀어 버려 P-14("명시적 재시도 성공 전까지 연습 모드")와 어긋난다. 큐 순서가 곧 확정 순서이므로 `last` 갱신 순서도 큐로 정해진다(G-11).
- **대안**: ① 페이지 소유 큐(언마운트 시 폐기·취소): G-4 위반이라 기각. ② React Context Provider에 보관: 가능하지만 테스트 주입이 복잡하고 모듈 단일 인스턴스 + `store` prop 주입과 효과가 같아 기각. ③ 게이트 없이 마지막 상태만 보관: 대기 중 쓰기를 막을 수 없어 기각.
- **주의**: 모듈 단일 인스턴스는 테스트 사이에 상태가 새지 않도록 테스트에서는 매번 새 인스턴스를 만드는 팩토리를 쓴다.

## R-18. IndexedDB 연결 오류 처리 (G-7)

- **결정**: 개별 트랜잭션 오류와 연결 무효화를 구분한다. 트랜잭션 `abort`/`error`는 연결을 닫지 않는다. 연결은 `versionchange`, `close` 이벤트, `InvalidStateError`, `open` 실패일 때만 무효화하고 **새 요청부터** 재연결한다. 진행 중인 요청은 강제로 종료하지 않는다. 연결 세대 번호는 도입하지 않고 요청이 자신의 연결 약속을 잡은 채 동일성 비교로 캐시를 비운다.
- **근거**: IndexedDB에서 트랜잭션 오류는 연결의 유효성과 무관하다. 오류마다 연결을 닫으면 같은 연결을 쓰던 다른 진행 중 읽기·쓰기를 불필요하게 실패시킨다(앱 이동 직후 기록 페이지의 읽기가 게임 페이지의 마지막 쓰기와 겹치는 상황). 동일성 비교로 "늦게 도착한 오래된 연결의 이벤트가 새 연결을 지우는" 문제가 해결되므로 세대 번호는 복잡도만 늘린다.
- **대안**: 오류마다 연결 닫기(이전 설계): 위 이유로 기각. 연결 세대 번호: 필요성이 관찰되지 않아 보류하며 필요해지면 근거와 함께 도입한다.

## R-19. 낭독 구조 (D1 승인: 단일 `role="status"`)

- **결정**: 결과 영역의 대표 live region 1개가 수동 결과·자동 실행·초기화·재시도·복구를 낭독하고, 오류는 `role="alert"`가 맡는다. 같은 사건은 한 영역만 낭독하며 자동 중단은 대표 status가, 수동 저장 실패는 `alert`가 맡는다. 시각 요약·진행·알림 박스는 live가 아니다. 책임표는 [contracts/ui-contract.md 6절](contracts/ui-contract.md).
- **근거**: v1 구조(결과 영역 안 `role="status"` 1개)를 유지하면서 자동 대결 중 낭독 폭주를 막는다(P-7). 컴포넌트별 live region(최종 HTML 방식)은 같은 사건이 둘 이상에서 낭독될 위험이 있어 사용자 결정으로 기각됐다.

## R-22. AC2-054("네트워크 요청 없음")와 `next/link` 프리페치 (실험 결과)

- **관찰**: 프로덕션 정적 빌드에서 `next/link`가 있는 페이지를 열면 첫 로드 때 **같은 출처의 정적 파일에 대한 `fetch` 요청**이 발생한다(`/rps-lab/__next._tree.txt`, `__next.__PAGE__.txt`, `history/__next.history.__PAGE__.txt` 등 6건과 페이지 URL 프리페치). 이 요청은 `dev`에서는 나타나지 않고 `next start`·정적 호스팅 어디서나 생긴다(GitHub Pages에 한정되지 않음). 외부 호스트 요청과 데이터 전송은 없다. 클릭 이동 때는 새 JS 청크 1개만 추가로 요청됐다.
- **쟁점**: AC2-054/FR2-023은 "게임·기록·통계 동작을 위한 서버 요청이 없고 개인정보를 수집하지 않으며 네트워크 요청이 없어야 한다"고 하며 검증은 Network 탭 확인이다. v1에는 `next/link`가 없어 이 문제가 없었다. 문자 그대로 읽으면 위 `fetch`가 위반으로 보일 수 있다.
- **선택지**: (a) 판정 기준을 명확화: 같은 출처의 정적 파일(HTML·JS·CSS·아이콘·`__next*.txt`) GET은 앱 로딩이므로 허용, 데이터 전송·API 호출·쿠키·외부 호스트 요청은 금지하고, `<Link prefetch={false}>`로 로드 시 자동 프리페치를 없애 요청이 이동 클릭 때만 생기게 함.
